# oscpm 0.1.0: OSC pattern matching and address space

Vocabulary follows `CONTEXT.md`. Decisions below respect ADR 0001 (C++17), ADR 0002 (`//` semantics) and ADR 0003 (non-owning `Pattern`).

## Problem Statement

Developers using oscpp can parse and build OSC packets in real-time contexts, but oscpp deliberately leaves address pattern matching to the caller. Its own suggestion, an exact-match hash table, silently ignores every wildcard in an incoming message. Anyone who needs `/synth/*/freq` or `//gain` to reach the right Methods today either writes a one-off matcher, copies a C implementation with an incompatible license, or takes on a full OSC framework that replaces oscpp rather than complementing it. No header-only C++ library exists that implements the OSC 1.0 wildcards plus the OSC 1.1 Descendant Operator, reports Malformed patterns distinctly from non-Matches, and stays allocation-free on the audio thread.

## Solution

oscpm: a header-only, dependency-free C++17 library under the zlib license that adds two things to an oscpp-style project.

1. A standalone matcher. A `Pattern` is parsed and validated once from a `string_view`, then tested against any number of Addresses with no allocation and no exceptions. Malformed input is a distinct result, never a non-Match.
2. An Address Space. Methods are registered at literal Addresses with a caller-chosen value type. A Lookup with a Pattern delivers every matching Method to a visitor, allocation-free. The Address Space can also be walked in address order for introspection.

An optional adapter header builds a `Pattern` from, or runs a Lookup for, an oscpp message directly. The API mirrors oscpp's naming so the two read as one library.

## User Stories

1. As an oscpp user, I want to match an incoming message's address pattern against my registered addresses, so that wildcard messages reach the right handlers instead of being dropped.
2. As an audio plugin developer, I want matching and Lookup to perform no heap allocation, so that I can run them inside the audio callback alongside oscpp.
3. As an audio plugin developer, I want matching and Lookup to never throw, so that my real-time code path has no hidden unwinding.
4. As an oscpp user, I want the library to be header-only with no dependencies, so that adding it is a copy of a directory or a CMake interface target.
5. As a developer on a non-oscpp stack such as JUCE, oscpack or liblo, I want the core to accept plain `string_view`, so that I can use the matcher without adopting oscpp.
6. As an oscpp user, I want an adapter that takes an oscpp message directly, so that I never convert types by hand at the call site.
7. As a developer, I want `?` to match exactly one byte within a Part, so that `/synth/?` matches `/synth/1` and not `/synth/12`.
8. As a developer, I want `*` to match zero or more bytes within a Part but never a `/`, so that `/synth/*` matches `/synth/freq` and not `/synth/1/freq`.
9. As a developer, I want Character Classes with ranges and negation, so that `/ch[1-4]` and `/ch[!0]` behave as the OSC 1.0 spec describes.
10. As a developer, I want Alternatives such as `/{amp,freq}`, so that one message can target several Methods by name.
11. As a developer, I want the Descendant Operator `//` from OSC 1.1, so that `//gain` reaches every Method named `gain` at any depth.
12. As a developer, I want `/a//b` to match `/a/b` as well as `/a/x/y/b`, so that `//` follows XPath's zero-or-more meaning as ADR 0002 records.
13. As a developer, I want a trailing `//` or a run of three slashes to be reported as Malformed, so that a typo never silently matches nothing.
14. As a developer, I want a nested brace or a bracket inside a brace to be reported as Malformed, so that unsupported syntax is loud rather than misinterpreted.
15. As a developer, I want an empty Alternative member in `{a,}` to match the empty string, so that the spec's "any of the comma-separated strings" is honoured literally.
16. As a developer, I want characters inside braces treated literally, so that `{a*,b}` cannot be mistaken for a wildcard inside an Alternative.
17. As a developer, I want `-` to be literal when first or last in a Character Class, so that `[a-]` and `[-a]` are usable.
18. As a developer, I want `[]`, `[!]` and an unterminated `[` reported as Malformed with the byte offset, so that I can point at the exact error in a log.
19. As a developer, I want matching to be byte-wise and case-sensitive, so that behaviour matches every other OSC implementation and needs no UTF-8 decoding.
20. As a developer, I want no escape mechanism, so that the library adds nothing beyond the published specs.
21. As a developer, I want an Address or Pattern without a leading slash, with an empty Part, with a trailing slash, or consisting of the bare root to be Malformed, so that ill-formed input is rejected at the boundary.
22. As a developer, I want to parse a `Pattern` once and match it many times, so that validation cost is paid off the hot path as ADR 0003 records.
23. As a developer, I want a one-call `match(pattern, address)` convenience, so that simple code stays simple.
24. As a developer, I want a tri-state match result of Match, NoMatch and Malformed, so that a switch over it has exactly three cases.
25. As a developer, I want every non-match error to carry an error kind and a byte offset, so that diagnostics can show where a pattern went wrong.
26. As a developer, I want a `Pattern` to hold only a view of the caller's bytes, so that it is trivially copyable and allocation-free, and I accept responsibility for the bytes' lifetime.
27. As a developer, I want to register a Method at a literal Address with a value of my own type, so that I can store a handler, an index or a pointer without a second map.
28. As a developer, I want the value type to be move-only friendly, so that I can store `unique_ptr` or capturing function objects.
29. As a developer, I want registration of an Address containing pattern characters to be rejected with a result code, so that a wildcard on the Address side is never silently meaningless.
30. As a developer, I want registration at an already-registered Address to be rejected, so that a typo never silently replaces a handler.
31. As a developer, I want to remove a Method by its Address, so that dynamic namespaces can shrink as well as grow.
32. As a developer, I want removal of an unknown Address to report NotFound, so that I can detect stale bookkeeping.
33. As a developer, I want an Address to be both a Container and a Method, so that `/synth` and `/synth/freq` can coexist.
34. As a developer, I want Lookup to call my visitor once per matching Method with the matched Address and a reference to the value, so that one handler can serve several Addresses.
35. As a developer, I want a const Lookup overload, so that I can match against an Address Space through a const reference.
36. As a developer, I want Lookup to return the number of Methods visited, so that I can detect an unrouted message cheaply.
37. As a developer, I want a convenience that fills a caller-provided span with matches, so that I can collect results without writing a visitor.
38. As a developer, I want an exact-Address Pattern to take a fast path, so that the common case of no wildcards costs a binary search per Part.
39. As a GUI developer, I want to walk the Address Space in address order, so that I can build a namespace browser or an OSC-query style reply.
40. As a developer, I want the Address Space documented as not thread-safe for concurrent mutation and Lookup, so that I know to build registration on the setup thread.
41. As a developer, I want registration to be allowed to allocate, so that the tree can grow without a fixed capacity.
42. As a developer, I want the API to mirror oscpp's naming style, so that mixed code reads as one library.
43. As a developer, I want the namespace to be lowercase `oscpm`, so that it is quick to type at every call site.
44. As a developer, I want three focused headers rather than one amalgamation, so that I include only the matcher if that is all I need.
45. As a build engineer, I want a CMake interface target with install and export, so that `find_package` works from a system install or a `FetchContent` pull.
46. As a build engineer, I want the oscpp adapter's CMake target to appear only when oscpp is found, so that the core target never carries a dependency.
47. As a build engineer, I want a clean build at `-Wall -Wextra -Wpedantic` and `/W4`, so that the header inherits no warnings into my project.
48. As a build engineer, I want the library verified on Apple Clang, GCC and MSVC, so that it builds wherever oscpp does.
49. As a developer, I want a README with a worked example, so that I can be productive within minutes.
50. As a developer, I want an example that feeds a hard-coded OSC packet through oscpp and the adapter with no sockets, so that the example builds everywhere.
51. As a contributor, I want a plain-text conformance corpus covering every spec rule and every ambiguity decision, so that the interpretation is documented by executable cases.
52. As a maintainer of another OSC library, I want the corpus to be plain text, so that I can reuse it against my own implementation.
53. As a contributor, I want the corpus reused through the Address Space, so that the tree path is proven against the same cases as the matcher.
54. As a security-minded developer, I want the parser fuzzed under ASan and UBSan, so that untrusted network bytes cannot crash the matcher.
55. As a maintainer, I want CI to run the compiler matrix and a short fuzz pass on every push, so that regressions are caught before release.
56. As a maintainer, I want semantic versioning from 0.1.0 with a version macro and a git tag per release, so that consumers can pin.
57. As a maintainer, I want a domain glossary and ADRs kept in the repo, so that future changes respect the decisions already made.

## Implementation Decisions

- Language and distribution: header-only C++17, zlib license, namespace `oscpm`, PascalCase types, camelCase functions. ADR 0001 records the departure from oscpp's C++11.
- Three public headers: the matcher, the Address Space, and the optional oscpp adapter. The core never includes oscpp.
- Matcher contract. `Pattern::parse` takes a `string_view` and returns either a `Pattern` or an error with kind and byte offset. `Pattern` holds a non-owning view and is trivially copyable. `Pattern::matches(address)` returns a tri-state `MatchResult` of Match, NoMatch or Malformed, where Malformed can arise only from the Address side since the Pattern was validated at parse. A free `match(pattern, address)` does parse-then-match. A free `validateAddress` checks a literal Address. ADR 0003 records the non-owning choice.
- Pattern semantics. OSC 1.0 wildcards `?`, `*`, Character Class, Alternative, plus the OSC 1.1 Descendant Operator. `//` matches zero or more whole Parts, is permitted leading or between Parts, and is Malformed trailing or as three or more slashes (ADR 0002). No nesting of braces, no brackets inside braces, empty Alternative members match the empty string, brace contents are literal. `-` is literal at either end of a Character Class; `[]`, `[!]` and unterminated `[` are Malformed. Byte-wise, case-sensitive, no escaping. A `]`, `}` or `,` outside its construct is Malformed, as is a Pattern Part longer than 8191 bytes (ADR 0004). Every Address and Pattern begins with `/` and has at least one non-empty Part; bare root, trailing slash and empty Parts are Malformed.
- Error model. One `Error` enum covering Malformed pattern, Malformed address, Duplicate, and NotFound, delivered as a small struct with a byte offset where meaningful. No exceptions anywhere in the library.
- Address Space. `AddressSpace<T>` requires T to be movable. Internally a tree of Containers and Methods with children in a sorted vector, binary-searched for exact Parts. A node may be both Container and Method. `add(address, T)` moves the value in and rejects Malformed and Duplicate. `remove(address)` reports NotFound. `lookup(pattern, visitor)` walks the tree with backtracking for `*`, Alternatives and `//`, calls the visitor as `(string_view address, T&)` once per Method, and returns the count; a const overload passes `const T&`. A span-filling convenience is built on the visitor. `forEach(visitor)` walks Methods in address order. Registration may allocate; Lookup may not. Concurrent mutation and Lookup are documented as unsupported.
- oscpp adapter. Two free functions: one that builds a `Pattern` from an oscpp server message, and one that runs a Lookup for a message. The adapter header includes oscpp's server header; the CMake target for it is created only when oscpp is found.
- Packaging. CMake interface target, install and export, `OSCPM_VERSION` macro, semantic versioning from 0.1.0.
- Build order. Milestone 1 the matcher and corpus; 2 the Address Space; 3 the adapter, example and README; 4 fuzzing, CI, install and export, tag 0.1.0. Each milestone ends in a commit with passing tests.

## Testing Decisions

A good test exercises the public API and asserts only what a consumer could observe: the match result, the error kind and offset, the sequence of visitor calls, and the return count. Tests must not inspect tree layout, node types or internal state. Real-time guarantees are tested by behaviour where possible, for instance a move-only T compiling and a Lookup succeeding with an allocation-counting global operator new asserting zero allocations.

Seams, highest first:

- Seam A, the matcher: `Pattern::parse`, `Pattern::matches`, `match`, and `validateAddress`. Driven by a plain-text conformance corpus with one case per line, grouped by spec rule and by each ambiguity decision. This is the single seam for pattern semantics.
- Seam B, the Address Space: `add`, `remove`, `lookup`, `forEach`. The same corpus is replayed through a populated Address Space so that the tree walk, including `//` backtracking, is proven against identical expectations. Additional cases cover Duplicate, NotFound, the Container-and-Method case, visitor order, and the const overload.
- The oscpp adapter gets a smoke test with a hand-built packet, plus the example program compiled in CI. It has no logic of its own worth a corpus.

Framework: Catch2 v3 pulled by CMake `FetchContent`. A libFuzzer target covers `Pattern::parse` and `match` under ASan and UBSan, one minute in CI and longer locally. No prior art exists in the repo; the corpus file is the pattern for all future conformance tests.

## Out of Scope

- Pattern-vs-pattern matching, where both sides carry wildcards.
- Callback dispatch with argument decoding; the visitor receives the stored value, not the message arguments.
- Bundle scheduling and timetags.
- Any pattern syntax beyond OSC 1.0 plus the 1.1 Descendant Operator, including CNMAT's backslash escape and rtosc's extensions.
- Thread-safe concurrent mutation of the Address Space.
- Code-point aware matching or any Unicode handling.
- Networking, sockets or transport of any kind.
- Benchmarks, Doxygen, package-manager manifests for vcpkg or Conan, and an amalgamated single header.
- C++11 or C++14 compatibility.

## Further Notes

- liblo's `//` implementation is LGPL; its source must not be copied. CNMAT's and rtosc's matchers are permissively licensed and may be consulted.
- The specs are silent on every ambiguity listed above; the corpus is the authoritative record of oscpm's interpretation and should be cited in the README.
- Design decisions were reached through a full interview whose settled outcomes are recorded in `CONTEXT.md` and `docs/adr/`.
